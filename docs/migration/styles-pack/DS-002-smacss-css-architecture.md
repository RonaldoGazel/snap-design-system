# SMACSS CSS Architecture Standard

## Purpose & Scope

This specification establishes SMACSS (Scalable and Modular Architecture for CSS) as the authoritative CSS architecture standard for all frontend development in the platform. It defines the five CSS categories (Base, Layout, Module, State, Theme), mandatory naming conventions (BEM for modules, SMACSS prefixes for layout and state), property ordering rules, selector performance guidelines, and explicit rules for both human developers and AI Agents.

DS-002 complements DS-001 (PrimeNG Design System Standard) by governing the CSS architecture layer that sits beneath and alongside the component library. DS-001 governs _which components_ to use; DS-002 governs _how to write and organize the CSS_ around and between those components.

### Why SMACSS Matters

- **Micro-frontend consistency**: Multiple teams and micro-frontends require a shared CSS architecture to prevent naming collisions, style conflicts, and maintenance chaos.
- **Brand consistency**: A unified CSS structure ensures that design tokens, spacing, typography, and colour palettes are applied consistently across all applications.
- **Development velocity**: Clear rules reduce decision fatigue, enable code review efficiency, and allow AI Agents to generate compliant CSS without human intervention.
- **Maintainability**: Modular CSS organized by category is easier to locate, modify, and refactor than monolithic stylesheets.

### Scope

DS-002 applies to:

- All custom CSS written by platform teams (Angular and React applications)
- All CSS generated by AI Agents (Kiro, Gemini, Cursor, Copilot, etc.)
- All preprocessor files (SCSS, Less) that compile to CSS

DS-002 does NOT apply to:

- Vendor stylesheets (e.g., PrimeNG component internals, third-party libraries)
- CSS-in-JS generated class names (though the style declarations must follow property ordering rules)
- Legacy CSS that predates this standard (migrate incrementally)

## SMACSS Overview

SMACSS (Scalable and Modular Architecture for CSS) is a methodology for organizing CSS into five distinct categories, each with its own rules, naming conventions, and use cases. This section provides a high-level introduction; detailed rules for each category follow in subsequent sections.

### The Five CSS Categories

Every CSS rule in the platform codebase must be classified into exactly one of these five categories:

#### 1. Base Rules

Base rules are the foundation — element selectors that define default styling for HTML elements without any class or ID selectors.

- **Selector type**: Element selectors only (e.g., `body`, `h1`, `a`, `input`)
- **Naming**: No prefix required
- **Purpose**: Establish minimal resets and default typography/spacing
- **Example**: `body { font-family: var(--font-family-base); }`

#### 2. Layout Rules

Layout rules define the structure and positioning of major page sections — grids, containers, columns, and page-level layouts.

- **Selector type**: Class selectors only
- **Naming prefix**: `l-` (e.g., `.l-grid`, `.l-container`, `.l-sidebar`)
- **Purpose**: Organize page structure without affecting component styling
- **Example**: `.l-grid { display: grid; grid-template-columns: repeat(12, 1fr); }`

#### 3. Module Rules

Module rules define reusable, self-contained components — buttons, cards, forms, modals, etc. Modules use strict BEM (Block\_\_Element--Modifier) notation.

- **Selector type**: Class selectors only
- **Naming convention**: BEM notation (mandatory)
  - **Block**: `.card`, `.search-form`, `.profile-card`
  - **Element**: `.card__title`, `.card__body`, `.card__footer`
  - **Modifier**: `.card--wide`, `.card__title--bold`
- **Purpose**: Create collision-free, reusable component styles
- **Example**: `.card { ... } .card__title { ... } .card--wide { ... }`

#### 4. State Rules

State rules define temporary, JavaScript-toggled conditions or structural variations.

- **Selector type**: Class selectors only
- **Naming prefix**: `is-` or `has-` for JavaScript-toggled states (e.g., `.is-active`, `.is-hidden`, `.has-error`)
- **Alternative**: BEM modifiers for structural/fixed variations (e.g., `.btn--large`, `.card--featured`)
- **Purpose**: Manage dynamic state changes and fixed variations separately
- **Example**: `.is-active { display: block; } .btn--large { padding: var(--space-4); }`

#### 5. Theme Rules

Theme rules define design tokens, colour palettes, typography scales, and spacing systems that enable brand swapping without modifying structural CSS.

- **Selector type**: CSS custom properties (variables) or preprocessor variables
- **Naming**: Semantic token names (e.g., `--bg-primary`, `--text-primary`, `--space-2`)
- **Purpose**: Centralize theme values for easy brand customization
- **Example**: `:root { --bg-primary: #ffffff; --text-primary: #000000; }`

### SMACSS Naming Prefixes

To quickly identify the category of any CSS class, SMACSS uses short prefixes:

| Category | Prefix         | Example                          |
| -------- | -------------- | -------------------------------- |
| Base     | (none)         | `body`, `h1`, `a`                |
| Layout   | `l-`           | `.l-grid`, `.l-container`        |
| Module   | (none)         | `.card`, `.btn`, `.search-form`  |
| State    | `is-` / `has-` | `.is-active`, `.has-error`       |
| Theme    | (none)         | `--bg-primary`, `--text-primary` |

### Key Principles

1. **One category per rule**: Every CSS rule belongs to exactly one category. A rule cannot be both a Layout and a Module rule.
2. **Shallow selectors**: Prefer specific class names over deeply nested descendant selectors. Shallow selectors are faster and more maintainable.
3. **No ID selectors for styling**: IDs are reserved for JavaScript hooks. Use class selectors exclusively for CSS.
4. **Design tokens over hardcoded values**: All colour, spacing, and typography values must reference CSS custom properties or preprocessor variables, never hardcoded literals.
5. **BEM for modules**: Module rules must use strict BEM notation to ensure collision-free naming across micro-frontends.

## Base Rules

**Rule**: Only element selectors are permitted in Base rules. No class or ID selectors.

**Rationale**: Base rules establish the foundation for all other CSS. By using only element selectors, Base rules apply globally without creating naming collisions or specificity conflicts. This approach supports a module-first architecture where components (Modules) are the primary building blocks, and Base rules provide minimal, non-intrusive defaults.

**Code Example — Correct Base Rules**:

```css
/* Base rules: element selectors only */
body {
  font-family: var(--font-family-base);
  font-size: var(--text-base);
  line-height: 1.5;
  color: var(--text-primary);
  background-color: var(--bg-primary);
}

h1,
h2,
h3,
h4,
h5,
h6 {
  font-weight: 600;
  line-height: 1.2;
  margin-bottom: var(--space-2);
}

a {
  color: var(--color-primary);
  text-decoration: none;
}

a:hover {
  text-decoration: underline;
}

input,
textarea,
select {
  font-family: inherit;
  font-size: inherit;
  border: 1px solid var(--border);
  padding: var(--space-1);
}

button {
  cursor: pointer;
  font-family: inherit;
  font-size: inherit;
}
```

**Anti-Pattern — Incorrect Base Rules**:

```css
/* ❌ WRONG: Using class selectors in Base rules */
.base-text {
  font-family: var(--font-family-base);
}

/* ❌ WRONG: Using ID selectors in Base rules */
#main-container {
  max-width: 1200px;
}

/* ❌ WRONG: Overly specific resets that conflict with modules */
.container h1 {
  font-size: 2rem;
}
```

## Layout Rules

**Rule**: All layout class names must use the `l-` prefix. Layout rules define page structure and positioning without affecting component styling.

**Rationale**: The `l-` prefix makes layout rules instantly recognizable and prevents naming collisions with Module rules. Layout rules are typically reusable grid systems, containers, and page-level positioning that sit outside the component layer.

**Code Example — Correct Layout Rules**:

```css
/* Layout rules: l- prefix on all class names */
.l-container {
  max-width: 1200px;
  margin: 0 auto;
  padding: 0 var(--space-4);
}

.l-grid {
  display: grid;
  grid-template-columns: repeat(12, 1fr);
  gap: var(--space-3);
}

.l-grid__col {
  grid-column: span 1;
}

.l-grid__col--span-6 {
  grid-column: span 6;
}

.l-sidebar {
  display: flex;
  gap: var(--space-3);
}

.l-sidebar__main {
  flex: 1;
}

.l-sidebar__aside {
  width: 300px;
}
```

**HTML Example**:

```html
<div class="l-container">
  <div class="l-grid">
    <div class="l-grid__col l-grid__col--span-6">
      <div class="card">
        <!-- Module content here -->
      </div>
    </div>
    <div class="l-grid__col l-grid__col--span-6">
      <div class="card">
        <!-- Module content here -->
      </div>
    </div>
  </div>
</div>
```

**Anti-Pattern — Incorrect Layout Rules**:

```css
/* ❌ WRONG: Layout class without l- prefix */
.container {
  max-width: 1200px;
}

/* ❌ WRONG: Layout rule using ID selector */
#page-grid {
  display: grid;
}

/* ❌ WRONG: Layout rule affecting component styling */
.grid .card {
  margin: 0;
}
```

## Module Rules (BEM)

**Rule**: All Module rules must use strict BEM (Block\_\_Element--Modifier) notation. Block names are lowercase-hyphenated nouns. Elements use `block__element` syntax with a maximum nesting depth of one level. Modifiers use `block--modifier` or `block__element--modifier` syntax and must always appear alongside the base Block class.

**Rationale**: BEM notation ensures collision-free naming across micro-frontends and teams. The strict structure makes CSS predictable and maintainable. Limiting element nesting to one level prevents deeply nested selectors that are hard to override and maintain.

**Code Example — Correct BEM Notation**:

```css
/* Block: the component itself */
.card {
  background-color: var(--bg-secondary);
  border: 1px solid var(--border);
  border-radius: var(--radius-md);
  padding: var(--space-3);
}

/* Element: parts of the block */
.card__header {
  display: flex;
  justify-content: space-between;
  align-items: center;
  margin-bottom: var(--space-2);
  border-bottom: 1px solid var(--border);
  padding-bottom: var(--space-2);
}

.card__title {
  font-size: var(--text-lg);
  font-weight: 600;
  color: var(--text-primary);
}

.card__body {
  margin-bottom: var(--space-2);
}

.card__footer {
  display: flex;
  gap: var(--space-2);
  justify-content: flex-end;
}

/* Modifier: variations of the block */
.card--wide {
  max-width: 100%;
}

.card--featured {
  border: 2px solid var(--color-primary);
  box-shadow: var(--shadow-md);
}

/* Modifier on element */
.card__title--bold {
  font-weight: 700;
}
```

**HTML Example**:

```html
<!-- Basic card -->
<div class="card">
  <div class="card__header">
    <h2 class="card__title">Card Title</h2>
  </div>
  <div class="card__body">
    <p>Card content goes here.</p>
  </div>
  <div class="card__footer">
    <button class="btn">Action</button>
  </div>
</div>

<!-- Card with modifiers: always include base class + modifier -->
<div class="card card--featured">
  <div class="card__header">
    <h2 class="card__title card__title--bold">Featured Card</h2>
  </div>
  <div class="card__body">
    <p>This card is featured.</p>
  </div>
</div>
```

**Icon Module Example**:

```css
/* Icon module: reusable icon component */
.icon {
  display: inline-block;
  width: 1em;
  height: 1em;
  vertical-align: -0.125em;
}

.icon__svg {
  width: 100%;
  height: 100%;
  fill: currentColor;
}

.icon--lg {
  width: 1.5em;
  height: 1.5em;
}

.icon--xl {
  width: 2em;
  height: 2em;
}

.icon--primary {
  color: var(--color-primary);
}

.icon--success {
  color: var(--color-success);
}
```

**Anti-Pattern — Incorrect BEM Notation**:

```css
/* ❌ WRONG: Nested BEM elements (more than one __ level) */
.card__header__title {
  font-size: 1.5rem;
}

/* ❌ WRONG: Naked modifier without base class */
.card--featured {
  border: 2px solid blue;
}
/* HTML: <div class="card--featured"></div> ← Missing .card base class */

/* ❌ WRONG: Contextual selector on BEM element */
.card .card__title {
  font-size: 1.5rem;
}

/* ❌ WRONG: Using tag-qualified class selector */
div.card {
  padding: 1rem;
}
```

## State Rules

**Rule**: Use `is-` or `has-` prefixed state classes for temporary, JavaScript-toggled conditions. Use BEM modifiers for structural or fixed variations. The `!important` declaration is permitted in state rules when necessary to ensure state styles override other specificity layers. Pseudo-class states (`:hover`, `:focus`, `:disabled`) must be defined within the module they affect.

**Rationale**: State rules and BEM modifiers serve different purposes. State classes represent temporary conditions that JavaScript toggles (e.g., `.is-active`, `.is-loading`), while BEM modifiers represent fixed variations (e.g., `.btn--large`, `.card--featured`). Separating these concerns makes CSS more predictable and easier to maintain. Pseudo-classes are scoped to their modules to keep related styles together.

**Code Example — Correct State Rules**:

```css
/* State class: temporary, JavaScript-toggled condition */
.is-active {
  background-color: var(--color-primary);
  color: var(--text-inverse);
}

.is-hidden {
  display: none !important;
}

.is-loading {
  opacity: 0.6;
  pointer-events: none;
}

.has-error {
  border-color: var(--color-danger);
}

/* BEM modifier: structural variation */
.btn--large {
  padding: var(--space-3) var(--space-4);
  font-size: var(--text-lg);
}

.btn--primary {
  background-color: var(--color-primary);
  color: var(--text-inverse);
}

/* Pseudo-classes defined within the module */
.btn:hover {
  background-color: var(--color-primary-dark);
}

.btn:focus {
  outline: 2px solid var(--color-primary);
  outline-offset: 2px;
}

.btn:disabled {
  opacity: 0.5;
  cursor: not-allowed;
}

/* State class on module element */
.form__input.is-invalid {
  border-color: var(--color-danger) !important;
  background-color: var(--color-danger-light);
}
```

**HTML Example**:

```html
<!-- Button with state class -->
<button class="btn btn--primary is-active">Active Button</button>

<!-- Button with pseudo-class (no class needed) -->
<button class="btn btn--primary">Hover me</button>

<!-- Form input with error state -->
<input type="text" class="form__input is-invalid" />

<!-- Loading state -->
<div class="card is-loading">
  <p>Loading...</p>
</div>
```

**Anti-Pattern — Incorrect State Rules**:

```css
/* ❌ WRONG: Using BEM modifier for temporary state */
.btn--active {
  background-color: blue;
}
/* This should be .is-active instead */

/* ❌ WRONG: Pseudo-class defined outside the module */
.card:hover {
  transform: scale(1.05);
}
/* Pseudo-classes should be in the .card rule block */

/* ❌ WRONG: State class without !important when needed */
.is-hidden {
  display: none; /* May not override higher specificity */
}
```

**Requirements addressed**: 2.5, 8.1, 8.2, 8.3, 8.4

## Theme Rules

**Rule**: Theme rules are separated into dedicated files to enable brand swapping without modifying structural CSS. All theme values (colours, typography, spacing) must be defined as CSS custom properties or preprocessor variables, never hardcoded values.

**Rationale**: Centralizing theme values in a separate layer enables rapid brand customization and ensures consistency across the entire application. By separating theme from structure, teams can swap brands without touching component CSS.

**Code Example — Correct Theme Rules**:

```css
/* _theme.css: Centralized design tokens */
:root {
  /* Colours */
  --color-primary: #6366f1;
  --color-primary-dark: #4f46e5;
  --color-primary-light: #818cf8;

  --color-success: #10b981;
  --color-warning: #f59e0b;
  --color-danger: #ef4444;
  --color-info: #3b82f6;

  --bg-primary: #ffffff;
  --bg-secondary: #f9fafb;
  --bg-tertiary: #f3f4f6;

  --text-primary: #1f2937;
  --text-secondary: #6b7280;
  --text-inverse: #ffffff;

  --border: #e5e7eb;

  /* Typography */
  --font-family-base:
    -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, sans-serif;
  --font-family-mono: "Courier New", monospace;

  --text-xs: 0.75rem;
  --text-sm: 0.875rem;
  --text-base: 1rem;
  --text-lg: 1.125rem;
  --text-xl: 1.25rem;

  /* Spacing */
  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-3: 1rem;
  --space-4: 1.5rem;
  --space-5: 2rem;

  /* Border radius */
  --radius-sm: 0.25rem;
  --radius-md: 0.5rem;
  --radius-lg: 1rem;
  --radius-full: 9999px;

  /* Shadows */
  --shadow-sm: 0 1px 2px 0 rgba(0, 0, 0, 0.05);
  --shadow-md: 0 4px 6px -1px rgba(0, 0, 0, 0.1);
  --shadow-lg: 0 10px 15px -3px rgba(0, 0, 0, 0.1);
}

/* Dark mode theme */
@media (prefers-color-scheme: dark) {
  :root {
    --bg-primary: #1f2937;
    --bg-secondary: #111827;
    --bg-tertiary: #0f172a;

    --text-primary: #f9fafb;
    --text-secondary: #d1d5db;
    --text-inverse: #1f2937;

    --border: #374151;
  }
}
```

```scss

$color-primary-dark: #4f46e5;
$color-success: #10b981;
$color-warning: #f59e0b;
$color-danger: #ef4444;

.btn {
  background-color: $color-primary;
  padding: $space-3 $space-4;

}
```

**Anti-Pattern — Incorrect Theme Rules**:

```css
/* ❌ WRONG: Hardcoded colour values in component CSS */
.btn {
  background-color: #6366f1; /* Should use var(--color-primary) */
}

/* ❌ WRONG: Hardcoded spacing in component CSS */
.card {
  padding: 1rem; /* Should use var(--space-3) */
}

/* ❌ WRONG: Theme values scattered across multiple files */
/* _button.css */
.btn {
  background-color: #6366f1;
}
/* _card.css */
.card {
  background-color: #6366f1;
}
/* Should be centralized in _theme.css */
```

## SMACSS + BEM Integration

**Overview**: SMACSS and BEM work together seamlessly. SMACSS provides the five-category framework for organizing CSS, while BEM provides the naming convention for Module rules. This section demonstrates how all five categories combine in a real-world component.

**Integration Blueprint**:

```html
<!-- Full SMACSS + BEM integration example -->
<div class="l-container">
  <!-- Layout rule: l-container -->

  <div class="l-grid">
    <!-- Layout rule: l-grid -->

    <div class="l-grid__col l-grid__col--span-8">
      <!-- Layout rules: l-grid__col (element), l-grid__col--span-8 (modifier) -->

      <article class="article article--featured">
        <!-- Module rule: article (block), article--featured (modifier) -->

        <header class="article__header">
          <!-- Module rule: article__header (element) -->

          <h1 class="article__title">
            <!-- Module rule: article__title (element) -->
            Featured Article
          </h1>

          <time class="article__date is-highlighted">
            <!-- Module rule: article__date (element) -->
            <!-- State rule: is-highlighted (temporary condition) -->
            March 15, 2025
          </time>
        </header>

        <div class="article__body">
          <!-- Module rule: article__body (element) -->

          <p>Article content with <a href="#" class="link">links</a>.</p>
          <!-- Base rule: a (element selector) -->
          <!-- Module rule: link (block) -->
        </div>

        <footer class="article__footer">
          <!-- Module rule: article__footer (element) -->

          <button class="btn btn--primary is-active">
            <!-- Module rule: btn (block), btn--primary (modifier) -->
            <!-- State rule: is-active (temporary condition) -->
            Read More
          </button>
        </footer>
      </article>
    </div>

    <aside class="l-grid__col l-grid__col--span-4">
      <!-- Layout rules: l-grid__col, l-grid__col--span-4 -->

      <div class="sidebar">
        <!-- Module rule: sidebar (block) -->

        <div class="sidebar__section">
          <!-- Module rule: sidebar__section (element) -->

          <h3 class="sidebar__title">Related Articles</h3>
          <!-- Module rule: sidebar__title (element) -->

          <ul class="sidebar__list">
            <!-- Module rule: sidebar__list (element) -->

            <li class="sidebar__item">
              <!-- Module rule: sidebar__item (element) -->
              <a href="#" class="link">Article 1</a>
            </li>
          </ul>
        </div>
      </div>
    </aside>
  </div>
</div>

<!-- Theme rules applied globally via CSS custom properties -->
<style>
  :root {
    --color-primary: #6366f1;
    --bg-primary: #ffffff;
    --text-primary: #1f2937;
    --space-3: 1rem;
    --space-4: 1.5rem;
  }
</style>
```

## Naming Conventions & Formatting

**Rule**: All CSS class names must follow SMACSS prefix conventions and BEM notation. CSS properties must be ordered in the mandated sequence: Positioning, Box Model, Typography, Visuals.

**Rationale**: Consistent naming makes CSS predictable and searchable. Property ordering improves readability and makes it easier to locate specific declarations within a rule block.

**SMACSS Prefix Conventions**:

| Category | Prefix         | Rule                                                   |
| -------- | -------------- | ------------------------------------------------------ |
| Base     | (none)         | Element selectors only; no prefix needed               |
| Layout   | `l-`           | All layout class names must start with `l-`            |
| Module   | (none)         | BEM notation; no prefix (block name is the identifier) |
| State    | `is-` / `has-` | All state class names must start with `is-` or `has-`  |
| Theme    | (none)         | CSS custom properties or preprocessor variables        |

**BEM Naming Rules**:

- **Block**: Lowercase, hyphenated, noun-based (e.g., `.card`, `.search-form`, `.profile-card`)
- **Element**: `block__element` with exactly one `__` separator (e.g., `.card__title`, `.card__body`)
- **Modifier**: `block--modifier` or `block__element--modifier` (e.g., `.card--featured`, `.card__title--bold`)
- **Modifier application**: Always apply the base Block class alongside the modifier (e.g., `class="card card--featured"`)

**Property Ordering**:

CSS properties must be ordered in this sequence:

1. **Positioning** — `position`, `top`, `right`, `bottom`, `left`, `z-index`
2. **Box Model** — `display`, `width`, `height`, `padding`, `margin`, `border`
3. **Typography** — `font-family`, `font-size`, `line-height`, `color`, `text-align`
4. **Visuals** — `background`, `box-shadow`, `opacity`, `transition`, `transform`

**Code Example — Correct Property Ordering**:

```css
/* Correct: properties ordered by category */
.card {
  /* Positioning */
  position: relative;
  z-index: 1;

  /* Box Model */
  display: flex;
  flex-direction: column;
  width: 100%;
  max-width: 400px;
  padding: var(--space-3);
  margin-bottom: var(--space-4);
  border: 1px solid var(--border);
  border-radius: var(--radius-md);

  /* Typography */
  font-family: var(--font-family-base);
  font-size: var(--text-base);
  line-height: 1.5;
  color: var(--text-primary);

  /* Visuals */
  background-color: var(--bg-primary);
  box-shadow: var(--shadow-sm);
  transition: box-shadow 0.2s ease;
}

.card:hover {
  box-shadow: var(--shadow-md);
}

.card--featured {
  /* Positioning */
  z-index: 2;

  /* Box Model */
  border: 2px solid var(--color-primary);

  /* Visuals */
  box-shadow: var(--shadow-lg);
}

.card__title {
  /* Box Model */
  margin: 0 0 var(--space-2) 0;

  /* Typography */
  font-size: var(--text-lg);
  font-weight: 600;
  color: var(--text-primary);
}
```

**Anti-Pattern — Incorrect Property Ordering**:

```css
/* ❌ WRONG: Properties scattered randomly */
.card {
  color: var(--text-primary);
  position: relative;
  background-color: var(--bg-primary);
  padding: var(--space-3);
  font-size: var(--text-base);
  z-index: 1;
  border: 1px solid var(--border);
  box-shadow: var(--shadow-sm);
}
```

## Anti-Patterns & Violations

**Overview**: This section lists prohibited CSS patterns and provides correct alternatives for each. CSS violating any of these patterns is non-compliant and must be corrected before merge.

### Prohibited Anti-Patterns

#### 1. Chained Descendant Selectors on BEM Elements

**Anti-Pattern**:

```css
/* ❌ WRONG: Chained descendant selector on BEM element */
.card .card__title {
  font-size: 1.5rem;
}
```

**Correct Alternative**:

```css
/* ✅ CORRECT: Direct class selector */
.card__title {
  font-size: var(--text-lg);
}
```

**Rationale**: Chained selectors increase specificity and make CSS harder to override. BEM elements are already specific; the chained selector is redundant.

---

#### 2. Nested BEM Elements (More Than One `__` Level)

**Anti-Pattern**:

```css
/* ❌ WRONG: Nested BEM elements */
.card__header__title {
  font-size: 1.5rem;
}
```

**Correct Alternative**:

```css
/* ✅ CORRECT: Single-level element */
.card__title {
  font-size: var(--text-lg);
}
```

**Rationale**: Limiting element nesting to one level keeps the naming flat and prevents deeply nested selectors. If you need to style a title within a header, use a single element name that describes the purpose.

---

#### 3. Naked Modifiers Without Base Class

**Anti-Pattern**:

```html
<!-- ❌ WRONG: Modifier applied without base class -->
<div class="card--featured">Featured card</div>
```

**Correct Alternative**:

```html
<!-- ✅ CORRECT: Base class + modifier -->
<div class="card card--featured">Featured card</div>
```

**Rationale**: Modifiers are variations of the base Block. Applying a modifier without the base class breaks the BEM contract and causes styles to not apply correctly.

---

#### 4. Contextual Selectors

**Anti-Pattern**:

```css
/* ❌ WRONG: Contextual selector */
.sidebar .btn {
  padding: 0.5rem;
}
```

**Correct Alternative**:

```css
/* ✅ CORRECT: Modifier on the component */
.btn--compact {
  padding: 0.5rem;
}

/* HTML: <button class="btn btn--compact">Action</button> */
```

**Rationale**: Contextual selectors create hidden dependencies between components. Using modifiers makes the variation explicit and reusable.

---

#### 5. ID Selectors for Styling

**Anti-Pattern**:

```css
/* ❌ WRONG: ID selector for styling */
#main-header {
  background-color: var(--bg-primary);
  padding: var(--space-4);
}
```

**Correct Alternative**:

```css
/* ✅ CORRECT: Class selector */
.header {
  background-color: var(--bg-primary);
  padding: var(--space-4);
}

/* HTML: <header id="main-header" class="header">...</header> */
```

**Rationale**: IDs are reserved for JavaScript hooks. Using IDs for styling creates high specificity that's hard to override and prevents reuse.

---

#### 6. Tag-Qualified Class Selectors

**Anti-Pattern**:

```css
/* ❌ WRONG: Tag-qualified class selector */
div.card {
  padding: var(--space-3);
}

button.btn {
  cursor: pointer;
}
```

**Correct Alternative**:

```css
/* ✅ CORRECT: Class selector only */
.card {
  padding: var(--space-3);
}

.btn {
  cursor: pointer;
}
```

**Rationale**: Tag-qualified selectors increase specificity and prevent the class from being reused on different element types. Class selectors are sufficient and more flexible.

---

#### 7. Deep Preprocessor Nesting (Beyond Two Levels)

**Anti-Pattern**:

```scss
/* ❌ WRONG: Deep nesting beyond two levels */
.card {
  padding: var(--space-3);

  .card__header {
    border-bottom: 1px solid var(--border);

    .card__title {
      font-size: var(--text-lg);

      &:hover {
        color: var(--color-primary);
      }
    }
  }
}
```

**Correct Alternative**:

```scss
/* ✅ CORRECT: Shallow nesting (max two levels) */
.card {
  padding: var(--space-3);

  &:hover {
    box-shadow: var(--shadow-md);
  }
}

.card__header {
  border-bottom: 1px solid var(--border);
}

.card__title {
  font-size: var(--text-lg);

  &:hover {
    color: var(--color-primary);
  }
}
```

**Rationale**: Deep nesting makes CSS harder to read and maintain. Limiting nesting to state changes and pseudo-classes keeps the structure flat and predictable.

---

#### 8. Hardcoded Values Instead of Design Tokens

**Anti-Pattern**:

```css
/* ❌ WRONG: Hardcoded colour and spacing values */
.btn {
  background-color: #6366f1;
  padding: 1rem 1.5rem;
  font-size: 16px;
}
```

**Correct Alternative**:

```css
/* ✅ CORRECT: Design token references */
.btn {
  background-color: var(--color-primary);
  padding: var(--space-3) var(--space-4);
  font-size: var(--text-base);
}
```

**Rationale**: Design tokens enable brand customization and consistency. Hardcoded values scatter theme information across the codebase and make updates difficult.

---

**Requirements addressed**: 4.1, 4.2, 4.3, 4.4

## Selector Performance & Depth of Applicability

**Rule**: The rightmost selector (key selector) in any CSS rule must be a class selector. Selectors must be shallow with minimal depth of applicability. Tag-qualified class selectors are prohibited.

**Rationale**: CSS selectors are evaluated right-to-left by the browser. The rightmost selector (key selector) is evaluated first and determines which elements are candidates for the rule. Using class selectors as the key selector is faster than tag selectors because classes are more specific and reduce the candidate set. Shallow selectors are also easier to maintain and override.

**Depth of Applicability** refers to the number of HTML generations a selector targets. For example:

- `.card` has depth 1 (targets direct elements with the class)
- `.card .card__title` has depth 2 (targets elements with class `card__title` that are descendants of `.card`)
- `.sidebar .card .card__title` has depth 3 (targets elements with class `card__title` that are descendants of `.card` that are descendants of `.sidebar`)

Shallow selectors (depth 1–2) are preferred over deep selectors (depth 3+).

**Code Example — Correct Selector Performance**:

```css
/* ✅ CORRECT: Class selector as key selector, shallow depth */
.card {
  padding: var(--space-3);
}

.card__title {
  font-size: var(--text-lg);
}

.btn {
  cursor: pointer;
}

.btn--primary {
  background-color: var(--color-primary);
}

/* ✅ CORRECT: Shallow descendant selector (depth 2) */
.card .card__title {
  /* Only if necessary; prefer direct class selector instead */
}

/* ✅ CORRECT: Pseudo-class selector with class key selector */
.btn:hover {
  background-color: var(--color-primary-dark);
}

.btn:focus {
  outline: 2px solid var(--color-primary);
}
```

**Anti-Pattern — Incorrect Selector Performance**:

```css
/* ❌ WRONG: Tag selector as key selector */
div.card {
  padding: var(--space-3);
}

/* ❌ WRONG: Deep descendant selector (depth 3+) */
.sidebar .card .card__title {
  font-size: var(--text-lg);
}

/* ❌ WRONG: Tag-qualified class selector */
button.btn {
  cursor: pointer;
}

/* ❌ WRONG: Overly specific selector */
html body .container .card .card__title {
  font-size: var(--text-lg);
}
```

**Requirements addressed**: 6.1, 6.2, 6.3

```css
  background-color: var(--color-primary);
  color: var(--text-inverse);
}

.search-form--compact {
  gap: var(--space-1);
}

.search-form__input--error {
  border-color: var(--color-danger);
}
```

### Rule 2: SMACSS Prefix Conventions

**Rule**: AI Agents must apply SMACSS prefix conventions correctly:

- Layout rules: `l-` prefix (e.g., `.l-grid`, `.l-container`)
- State rules: `is-` or `has-` prefix (e.g., `.is-active`, `.has-error`)
- Module and Base rules: no prefix

**Example**:

```css
/* ✅ CORRECT: AI-generated SMACSS prefixes */
.l-sidebar {
  /* Layout rule */
}
.l-grid__col {
  /* Layout rule with BEM */
}
.card {
  /* Module rule */
}
.is-active {
  /* State rule */
}
.has-error {
  /* State rule */
}
```

---

### Rule 3: Design Token Usage (No Hardcoded Values)

**Rule**: AI Agents must reference CSS custom properties (`var(--...)`) or preprocessor variables (`$...`) for all colour, spacing, and typography values. Hardcoded literal values are prohibited.

**Example**:

```css
/* ✅ CORRECT: AI-generated CSS with design tokens */
.btn {
  background-color: var(--color-primary);
  padding: var(--space-2) var(--space-3);
  font-size: var(--text-base);
  border-radius: var(--radius-md);
}

/* ❌ WRONG: AI-generated CSS with hardcoded values */
.btn {
  background-color: #6366f1;
  padding: 0.5rem 1rem;
  font-size: 16px;
  border-radius: 0.5rem;
}
```

---

### Rule 4: Selective Section Loading

**Rule**: AI Agents must load only the relevant section of DS-002 for the current task, not the entire document. Use `spec-index.md` tags to identify which sections are needed.

**Example**:

- Task: "Generate a button component" → Load "Module Rules (BEM)" section
- Task: "Create a page layout" → Load "Layout Rules" section
- Task: "Add a loading state" → Load "State Rules" section

---

### Rule 5: Self-Correction on Violations

**Rule**: If an AI Agent generates CSS that violates any rule in DS-002, the Agent must flag the violation, correct the output, and present the corrected version to the developer with an explanation of the fix.

**Example**:

```
Developer: "Generate a card component"

AI Agent Output (with self-correction):

⚠️ VIOLATION DETECTED: Initial output used hardcoded colour #6366f1
✅ CORRECTED: Changed to var(--color-primary)

⚠️ VIOLATION DETECTED: Initial output used nested BEM element .card__header__title
✅ CORRECTED: Changed to .card__title

Here is the corrected CSS:

.card {
  background-color: var(--bg-secondary);
  padding: var(--space-3);
  border-radius: var(--radius-md);
}

.card__title {
  font-size: var(--text-lg);
  font-weight: 600;
}
```

---

### Rule 6: Property Ordering Compliance

**Rule**: AI Agents must order CSS properties in the mandated sequence: Positioning, Box Model, Typography, Visuals.

**Example**:

```css
/* ✅ CORRECT: AI-generated CSS with proper property ordering */
.card {
  /* Positioning */
  position: relative;
  z-index: 1;

  /* Box Model */
  display: flex;
  flex-direction: column;
  padding: var(--space-3);
  margin-bottom: var(--space-4);
  border: 1px solid var(--border);

  /* Typography */
  font-family: var(--font-family-base);
  font-size: var(--text-base);
  color: var(--text-primary);

  /* Visuals */
  background-color: var(--bg-secondary);
  box-shadow: var(--shadow-sm);
}
```

---

### Rule 7: No Overriding PrimeNG Component Internals

**Rule**: In Angular applications, AI Agents must not generate CSS that targets PrimeNG internal component selectors (e.g., `.p-button-label`, `.p-datatable-header`). Custom SMACSS rules must complement PrimeNG's design token system without overriding component internals. (See DS-001 for PrimeNG theming rules.)

**Example**:

```css
/* ✅ CORRECT: Custom SMACSS CSS for Angular */
.card {
  background-color: var(--bg-secondary);
  padding: var(--space-3);
}

/* ❌ WRONG: Overriding PrimeNG internals */
.p-button-label {
  font-size: 1rem;
}

.p-datatable-header {
  background-color: #f9fafb;
}
```

## Enforcement & Compliance

**Overview**: This section defines how SMACSS violations are detected, reported, and resolved.

### Compliance Rule

**Rule**: CSS code violating any rule in DS-002 is non-compliant and must be corrected before merge. No exceptions without explicit team lead approval and documented justification.

### Violation Detection Methods

| Method        | Scope                     | Timing                   | Responsibility |
| ------------- | ------------------------- | ------------------------ | -------------- |
| Code review   | All CSS changes           | Pre-merge (pull request) | Code reviewer  |
| CSS linting   | Automated subset of rules | CI pipeline              | CI/CD system   |
| AI self-check | AI-generated CSS          | During generation        | AI Agent       |

### Violation Response Procedure

#### 1. Code Review Violation

When a code reviewer identifies a DS-002 violation:

1. **Reference the specific section**: "This violates DS-002 Section 3.2 (BEM Notation)"
2. **Provide the correct alternative**: Show the corrected code
3. **Request correction**: Developer must fix before merge

**Example**:

```
Reviewer comment:
"This violates DS-002 Section 3.2 (BEM Notation).
Nested BEM elements (.card__header__title) are prohibited.
Use .card__title instead.

Correct:
.card__title { ... }
```

#### 2. CI Lint Failure

When the CI pipeline detects a violation:

1. **Block merge**: The pull request cannot be merged until the violation is fixed
2. **Provide lint output**: Show which rule was violated and where
3. **Developer fixes**: Developer corrects the code and re-submits

#### 3. AI Agent Violation

When an AI Agent generates CSS that violates DS-002:

1. **Agent flags the violation**: "⚠️ VIOLATION DETECTED: ..."
2. **Agent corrects the output**: "✅ CORRECTED: ..."
3. **Agent presents corrected version**: Developer reviews and accepts the corrected code

#### 4. Deviation Request

If a developer needs to deviate from DS-002:

1. **Document the justification**: Add a code comment explaining why the deviation is necessary
2. **Obtain team lead approval**: Get explicit approval from the team lead
3. **Record the decision**: Document the deviation in the pull request description

**Example**:

```css
/* DEVIATION: Using ID selector for JavaScript hook (approved by @team-lead) */
/* Justification: This ID is used by a third-party library that requires ID-based selection */
#analytics-container {
  /* CSS here */
}
```

### Violation Categories

| Category                         | Severity | Action                             |
| -------------------------------- | -------- | ---------------------------------- |
| BEM notation violation           | High     | Block merge, require correction    |
| Hardcoded value instead of token | High     | Block merge, require correction    |
| ID selector for styling          | High     | Block merge, require correction    |
| Deep nesting (>2 levels)         | Medium   | Flag in review, request correction |
| Tag-qualified class selector     | Medium   | Flag in review, request correction |
| Contextual selector              | Medium   | Flag in review, request correction |
| Property ordering                | Low      | Flag in review, suggest correction |

## Cross-References

### Related Specifications

**DS-001: PrimeNG Design System Standard**

DS-002 complements DS-001 by defining the CSS architecture layer beneath the component library. DS-001 governs _which components_ to use; DS-002 governs _how to write and organize the CSS_ around and between those components.

- **DS-001 theming**: PrimeNG uses `definePreset` to customize design tokens. DS-002 uses CSS custom properties to reference those tokens.
- **DS-001 component usage**: PrimeNG components are pre-styled and should not be overridden. DS-002 provides rules for custom CSS that complements PrimeNG.
- **Cross-reference**: See DS-001 Section "Theming and Brand Customisation" for PrimeNG-specific theming rules.

### AI Agent Specifications

**AI-002: Context Loading**

AI Agents use `spec-index.md` to discover and load relevant specifications. DS-002 is tagged with `design-system, smacss, css, bem, architecture, naming-conventions` to enable selective loading.

- **Selective loading**: When an AI Agent is asked to generate CSS, it should load only the relevant DS-002 sections (e.g., "Module Rules" for component CSS, "Layout Rules" for page structure).
- **Context efficiency**: Loading only relevant sections reduces context overhead and improves response quality.

**AI-007: Architecture Compliance**

AI Agents must validate generated code against architecture standards. DS-002 defines the CSS architecture standard that AI Agents must comply with.

- **Validation**: AI Agents should validate generated CSS against DS-002 rules before presenting to developers.
- **Self-correction**: If violations are detected, AI Agents should correct the output and explain the fixes.
